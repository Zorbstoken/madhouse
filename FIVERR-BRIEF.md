# FIVERR BRIEF — Game Design Consultant (copy-paste ready)

## Title for the gig posting
Game design consultant needed: tighten the design document for a Telegram-based social economy game (fixed-supply currency, youth movement launch)

## What the game is (paste this)
MADHOUSE is a meeting engine disguised as a game. Players join via a Telegram bot, play personality games, get matched with like-minded peers, trade in a fixed-supply Dot economy (1,000,000 Dots, never printed), buy game goods at an NPC shop, publish wishes, and complete community quests. The Dots aren't the point — they're the excuse. The point is young people meeting each other as free, sovereign, independent humans. Launch: November 20, 2026 (International Youth Walkout). Four design filters everything must pass: (1) does it help people meet each other? (2) the grandparents' question — does it make money? (3) the twelve-year-old's test — learnable in one showing? (4) the wholesomeness test — no dark patterns, no extraction.

## What exists (you'll receive all of this)
- Working engine: single ledger, conservation-tested (614 tests green), gift/trade by unique token, 5 NPCs on seeded purses, shop, 202 quests, offer/need exchange, matching engine with named reasons, wish board
- Design docs: system documentation, game design review (unsparing, lists every gap), engine vision, API contract v6, flow-review brief with playtest script
- Telegram bot verified with Telegram (needs a host); web front end + Mini Apps

## What we need from you — the 15 workstreams
For each: assess what exists, name what's missing, and write the tightened spec. One section per workstream, plain words, no jargon.

1. **High concept & pillars** — sharpen the one-paragraph pitch and 3–5 design pillars
2. **Player fantasy & audience** — who is the player, what do they dream of becoming here?
3. **Core loop** — the minute-to-minute: what's the smallest satisfying action cycle?
4. **Meta loop** — the day-to-day: why come back tomorrow? (our weakest area — be brutal)
5. **Economy design** — sources, sinks, velocity. We have fixed supply + conservation; stress-test it: where does it stagnate, where does it leak?
6. **Progression systems** — what accumulates across days? (currently nothing — design it)
7. **Social systems** — packs (3–12), trust ladder (playful → vouched → verified), meeting mechanics
8. **Quest/content design** — 202 quests exist; design the completion loop (report-back → acknowledgment → reward) and the content pipeline
9. **Narrative/lore integration** — the Zorbs universe codex meets the game controls; how does lore become mechanics?
10. **UX/UI flows** — map every screen from join to endgame; flag every dead end
11. **Art direction** — the game is theater; define the visual register (we have poster art; the in-game look is open)
12. **Audio/music direction** — Telegram-native: what does the game sound like?
13. **Technical architecture review** — is the single-ledger engine sound for 10,000 players? Name the breaking points
14. **QA & playtesting plan** — script synthetic playtests (five player archetypes incl. a trickster and a 15-year-old who must be refused kindly); adversarial cases (double-spend, farming, token replay)
15. **Live ops & seasons** — the 30 days after the walkout: three beats minimum. Launches die in December without a second act

## Hard constraints (non-negotiable)
- No minors in matching/contact features under 16 — design around this, never through it
- Admin sees aggregates only — no feature may expose individual players
- Fixed supply is sacred — no minting, no negative balances, NPCs never print
- No loot boxes, no gacha, no pay-to-win, no randomness sold as gameplay

## Deliverable
One tightened Game Design Document (GDD): the 15 sections above, each with verdict (keep/fix/cut), the fix specified as the smallest shippable step, and an honest gaps list ranked by launch criticality. Markdown is fine.
